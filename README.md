# Gitea イシュー自動返信キット

Gitea にイシューを立て、ラベルを 1 つ付けると、**AI がコードベースや設計書を調査して
コメントで返信する**仕組み一式です。そのまま配置して動かせます。

```
テンプレートからイシュー作成（help-AI ラベルが自動で付く）
        ▼
Gitea Actions が起動 → 「調査中です」コメントを投稿
        ▼
参照リポジトリ（コード・設計書・wiki）を取得
        ▼
イシュー本文・既存コメント・取得結果をプロンプトに埋め込んで Claude Code CLI を実行
        ▼
生成された返信で、さきほどのコメントを書き換える
        ▼
help-AI ラベルを外す（追加質問は コメント → ラベル再付与 で再実行）
```

- **調査して答えるだけ。** コードの修正・コミット・PR 作成はしません（ツール権限でも禁止）
- **契約プランの枠内で動きます。** 認証は OAuth トークン。従量課金の API キーは使いません
  （枠を超えたときは課金ではなく、リセット時刻を添えて失敗します）
- **手元でテストできます。** 通信せずに、判定・取得・プロンプト・API 呼び出しを確かめられます

## 使いはじめる

```bash
bash scripts/install.sh /path/to/your-repo   # 配置
# refs.json を自分の参照リポジトリに書き換える
# SKILL.md の「前提環境」の表を refs.json と揃える
python3 scripts/check_sync.py                # 一覧の食い違いを検査
```

あとは Secrets（`CLAUDE_CODE_OAUTH_TOKEN` / `BOT_TOKEN` / `BOT_LOGIN` / `REF_TOKEN`）を登録し、
`help-AI` ラベルを作れば動きます。手順は **[docs/セットアップ.md](docs/セットアップ.md)** に。

## 中身

**どこに何があるかは [docs/フォルダ構成.md](docs/フォルダ構成.md) にまとめてあります**（ツリーは実体と自動照合）。

```
gitea-ai-issue-reply/
├── workflows/ai-issue-reply.yml      ワークフロー（→ .gitea/workflows/）
├── skills/issue-ai-reply/SKILL.md    AI 向けの実行指示（→ .claude/skills/）
├── issue-templates/ask_ai.yaml       質問テンプレート（→ .gitea/ISSUE_TEMPLATE/）
├── refs.json                         参照リポジトリの一覧（ここだけ書き換える）
├── scripts/
│   ├── gate.sh          起動条件の判定（PR 除外・ラベル判定・二重起動の抑止）
│   ├── clone_refs.sh    参照リポジトリの取得（1 つ失敗しても続行、.git は捨てる）
│   ├── build_prompt.sh  イシュー本文・コメント・取得結果からプロンプトを作る
│   ├── run_claude.sh    Claude Code CLI の実行（フラグを事前検証・利用上限を検出）
│   ├── usage_limit_message.sh  利用上限に達したときの文面（リセット時刻を JST で）
│   ├── gitea_api.sh     コメントの作成・書き換え、ラベル操作（DRY_RUN 対応）
│   ├── check_sync.py    参照一覧の食い違い検査（refs.json / SKILL.md / 運用仕様.md）
│   ├── check_tree.py    ドキュメントのツリーと実体の照合
│   └── install.sh       配置
├── docs/
│   ├── フォルダ構成.md        どこに何があるか（入口）
│   ├── セットアップ.md        導入手順
│   ├── 運用仕様.md            人向けの仕様（利用者・運用者）
│   ├── 設計判断.md            なぜこの形か（踏んだ落とし穴と対処）
│   └── トラブルシュート.md    症状別の切り分け
└── tests/                    全部品のテスト（通信しない）
```

## テスト

```bash
bash tests/run_all.sh
```

外部へは一切接続しません。`git` と `claude` は偽の実行ファイルに差し替え、
Gitea API は `DRY_RUN` で要求内容だけを確認します。

| テスト | 確かめること |
| --- | --- |
| `test_gate.sh` | ラベル単独／複数同時／別ラベル追加／PR／ラベル無しの各場合の起動可否 |
| `test_clone_refs.sh` | 浅い取得、失敗しても続行、`.git` の削除、トークンを出力しない、sparse 指定 |
| `test_build_prompt.sh` | 本文・コメントの埋め込み、自分の過去返信の識別、取得結果の受け渡し |
| `test_gitea_api.sh` | メソッドと URL、本文の JSON 化、トークンを出さないこと |
| `test_run_claude.sh` | 引数の組み立て、フラグ名が違えば起動前に落ちること、空返信・異常終了の扱い |
| `test_check_sync.py` | 3 か所の一覧の食い違い検出 |
| `test_layout.sh` | 配置後に動くか、YAML が妥当か、呼ぶスクリプトが揃っているか |

## 設計上の要点

詳しい理由は [docs/設計判断.md](docs/設計判断.md) にあります。要点だけ:

| 決めごと | 理由 |
| --- | --- |
| トリガーは `labeled` のみ＋イシュー番号ごとの `concurrency` | イシュー作成時は `opened` と `labeled` が両方発火し、二重返信になる |
| 起動判定はワークフローの `if:` ではなくスクリプト | payload の形が Gitea 実装依存。かつ手元でテストできる |
| 参照リポジトリは 1 つ失敗しても続行、欠落は一覧で出す | 資料が 1 つ欠けるより、返信が 1 件も出ないほうが痛い |
| 取得後に `.git` を捨てる | clone URL のトークンが `.git/config` に残り、AI が読めてしまう |
| 本文はワークフロー側で埋め込む | AI にイベントファイルを読ませないことで `Bash` を禁止できる |
| `Bash` / 書き込み系 / Web 系を禁止 | 本文は外部入力。指示だけでは強制にならない |
| CLI フラグを起動前に検証 | 版でフラグ名が変わる。走ってから落ちると切り分けに時間がかかる |
| 認証は契約プランの OAuth トークン | API キーは従量課金。枠超過が「課金」ではなく「失敗」になる方を選ぶ |
| API キーと OAuth の両立を検出したら止める | どちらが優先されるかは環境依存で、意図せず課金される側で動きうる |
| ラベルは成否にかかわらず外す | 残ると同じラベルを付け直せず、再実行できない |

## 既製のアクションを使う構成にする場合

このキットは Claude Code CLI を直接呼びます。Gitea 向けの既製アクション
（イシューの取得・プレースホルダ投稿・コメント更新まで面倒を見るもの）を使う構成でも構いません。
その場合は次を置き換えます。

- `④ 作業中コメント` 〜 `⑧ 返信を投稿` を、アクションの呼び出し 1 ステップに差し替える
- プロンプトはアクションが埋め込むので、`build_prompt.sh` は不要になる
- ツール権限は、アクションの `disallowed_tools` 相当の入力で同じものを禁止する

**アクション本体はバージョン（SHA）で固定してください。** 上流の更新で、ジョブ内で実行される
内容が予告なく変わります。参照リポジトリ（読むだけのデータ）を `main` で追うのとは別の話です。

## 制限

- 返信は 1 回のやりとりで完結します。会話の履歴は、イシューのコメントとして残っているものだけです
- Excel・Word・PowerPoint は読めません。同じ内容が別形式（Markdown・PDF・生成元の定義ファイル）で
  あればそちらを参照させてください。無ければ「確認できていない」と返ります
- 実装まで自動化するものではありません（[運用仕様](docs/運用仕様.md#責務の範囲)）
