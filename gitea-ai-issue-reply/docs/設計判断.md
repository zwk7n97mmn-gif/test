# 設計判断

📍`🏠ホーム > 📁Giteaイシュー自動返信キット > 設計判断`

---


なぜこの形なのかを残します。多くは「一度踏んだ落とし穴」への対処です。
同じ仕組みを作り直すとき、ここを読めば同じ穴を避けられます。

## トリガーは `labeled` だけにする

イシュー作成時、Gitea は `opened` と `labeled` の**両方**を発火します。
テンプレートでラベルを自動付与する構成では、`opened` も拾うと同じイシューに 2 つのジョブが
起動し、**返信が 2 件付きます**（1 秒差で同時に走るため、後から気づきにくい）。

`labeled` だけにしたうえで、さらにイシュー番号ごとの `concurrency` で直列化します。
トリガー種別を絞るだけでは、ラベルの同時付与・連続付与で再発しうるためです。

## 起動条件はワークフローの `if:` ではなくスクリプトで判定する

ラベル付与時の payload の形（`.label` か `.changes.added_labels` か）は Gitea の実装により
異なり、式評価器の object filter 対応にも差があります。`jq` で payload を直接読むほうが確実です。

副次的な利点として、**手元でテストできます**（`tests/test_gate.sh`）。
判定の分岐は次の 3 つで、どれも実際に踏む条件です。

| 条件 | なぜ必要か |
| --- | --- |
| PR を除外する | イシューと番号空間を共有しているため、PR にラベルを付けても発火する |
| 現在のラベルを見る | 外した直後の再発火などで、ラベルが無い状態で起動することがある |
| 今回付与されたラベルを見る | `help-AI` が残ったまま別のラベルを足すと、再び発火してしまう |

## 参照リポジトリの取得は「1 つ失敗しても続ける」

参照リポジトリは「あれば精度が上がる」ものです。1 つ欠けても残りの資料で回答できます。
一方、取得の失敗でジョブごと落ちると**返信が 1 件も出ません**。損失が非対称なので、
個別の失敗は握りつぶし、**どれが欠けたかを一覧で出す**方針にしています。

欠落は AI へのプロンプトにも `<reference_repos>` として渡します。
これが無いと、AI は「資料が見つからない」という前提で回答を書いてしまい、
読む側からは原因が分かりません。

改名にも注意が必要です。Gitea は旧名への API 要求を 301 で新名へ転送しますが、
**git の clone はリダイレクトを追いません**。旧名のままだと `Not found` になり、
権限不足とまったく同じ文言が出ます。

## 取得後に `.git` を捨てる

clone URL にトークンを載せる方式（`x-access-token:<PAT>@`）では、`.git/config` に
トークンが平文で残ります。AI には `Read` を許可しているので、**残せば読めてしまいます**。
参照リポジトリは取得後に git 操作をしないため、`.git` ごと削除します。

## イシュー本文はワークフロー側でプロンプトに埋め込む

AI 自身にイベントファイル（`$GITHUB_EVENT_PATH`）を読ませる作りにすると、
`Bash` を許可しなければならなくなります。すると `sed -i` での書き換え、`git push`、
`curl` での外部送信の経路が同時に開きます。

本文・コメントを**先に埋め込んでしまえば `Bash` を禁止できます**。
これが、返信の責務（読んで答えるだけ）とツール権限を一致させる一番簡単な方法です。

## ツール権限で落とす（指示だけに頼らない）

イシュー本文は外部からの入力です。「分析・回答までに留める」という SKILL.md の記述は
**指示にすぎず、技術的な強制ではありません**。`Edit` / `Write` / `Bash` / `WebFetch` /
`WebSearch` を禁止し、残すのは `Read` / `Grep` / `Glob` だけにします。

## CLI のフラグは起動前に検証する

Claude Code CLI のフラグ名は版によって変わることがあります。実行してから
「そんなオプションは無い」で落ちると、原因の切り分けに時間がかかります。
`--help` の出力と突き合わせ、**合わなければ起動せず、どのフラグが無いかを出して終了**します。

同じ考えで、環境変数による上限指定にも注意が必要です。値の範囲に制限があるものを
範囲外の値で設定すると、**プロセスが起動する前に落ちます**（返信が 1 件も出ません）。
上限を上げたいときは、その手段が本当に効くのかを先に確かめてください。

## 認証は契約プランの OAuth トークンにする（従量課金の API キーを使わない）

同じ Claude を動かすのでも、認証の種類で費用のかかり方が変わります。

| 方式 | 費用 | 枠を超えたとき |
| --- | --- | --- |
| API キー（`ANTHROPIC_API_KEY`） | 従量課金。使った分だけ請求される | 請求が増えるだけで、動き続ける |
| OAuth トークン（`CLAUDE_CODE_OAUTH_TOKEN`） | 契約プランの枠を消費。追加請求なし | **失敗して止まる** |

「追加課金を絶対に発生させない」なら後者です。**上限に達したときの挙動が
『黙って課金』ではなく『はっきり失敗』になる**ことが、この選択の実質的な意味です。

そのぶん、上限に達したときの扱いを用意しておく必要があります。何も出ないと
「返信が来ない」という事実だけが残り、ジョブログを開くまで理由が分かりません。
失敗の文面に**リセット時刻（JST）と再実行の方法**まで書きます。

時刻の組み立てでは `TZ=Asia/Tokyo` を使いません。ランナーに tzdata が無いと
黙って無視され、**UTC の時刻を JST と書いてしまう**ためです。UTC 固定で +9 時間します。

両方の認証情報が設定されている状態も防ぎます。どちらが優先されるかは環境に依存し、
意図せず課金される側で動きうるため、**両立を検出したら起動せずに止めます**。

## 「調査中」コメントを先に出し、同じコメントを書き換える

返信の生成には 10〜20 分かかります。何も出ないと、動いているのか失敗したのか分かりません。
新しいコメントを足すのではなく**同じコメントを書き換える**ことで、イシューの見通しも保てます。

失敗したときも、そのコメントを失敗の旨に書き換えます。黙って終わると
「返信が来ない」という事実だけが残り、原因を追う手がかりがありません。

## ラベルは成否にかかわらず外す

失敗時にラベルが残ると、**同じラベルを付け直せず再実行できません**（付け直すには
一度外す必要があり、その操作自体が発火条件になります）。
「返信コメントが付いていなければ失敗」と判断できるようにしておくほうが、運用が単純です。

## 一覧は 3 か所を同時に直す

参照リポジトリの一覧は、`refs.json`（取得する）・`SKILL.md`（AI に教える）・
`運用仕様.md`（人が読む）の 3 か所に現れます。片方だけ直すとズレます。

- `refs.json` にだけ足した … clone はされるが、AI が参照先として知らず調査に使われない
- `SKILL.md` にだけ足した … AI が存在しないディレクトリを読もうとして無駄に試行する

`scripts/check_sync.py` が食い違いを検出します。CI に入れておくと、直し忘れがマージされません。

## 参照データは `main` を追い、実行コードは固定する

参照リポジトリ（調査対象）は最新を読みます。固定すると古い内容で回答してしまうためです。
一方、**ジョブ内で実行されるもの**（アクションを使う構成ならそのアクション本体）は
バージョンを固定します。上流の更新で実行内容が予告なく変わるためです。

## 改行コードを固定する

Windows で編集したワークフローや `.sh` が CRLF のままコミットされると、Linux のランナーが
行末の CR まで引数に含めて失敗します（`set: pipefail\r: invalid option name` の形）。
`.gitattributes` で `.yml` / `.yaml` / `.sh` / `.py` を LF に固定します。
