# イシュー自動返信の運用仕様

`help-AI` ラベルを付けたイシューに、AI がコードベース・Wiki・設計書を調査して返信する機能の仕様です。

- 利用者向け: 「使い方」「返信の内容」「所要時間と挙動」
- 運用・保守向け: 「構成」「処理の流れ」「権限とセキュリティ」「責務の範囲」

| ファイル | 役割 |
| --- | --- |
| `.gitea/workflows/ai-issue-reply.yml` | ワークフロー定義（トリガー・取得・ツール権限） |
| `.gitea/scripts/` | 判定・取得・プロンプト組み立て・API 呼び出し |
| `.claude/skills/issue-ai-reply/SKILL.md` | AI 向けの実行指示。**本書は人向け、SKILL.md は AI 向け** |
| `.gitea/ISSUE_TEMPLATE/ask_ai.yaml` | 質問イシューのテンプレート |
| `refs.json` | 参照リポジトリの一覧 |

## 使い方

### 新規に質問する

1. イシュー作成時にテンプレート「AIに質問する」を選ぶ
2. 種別・概要・対象・詳細を記入して作成する
3. `help-AI` ラベルが自動で付き、返信が始まる

回答の精度は入力情報の具体性に比例します。対象の機能・ファイル名・テーブル名・再現手順が
書かれているほど、調査が正確になります。

### 追加で質問する

返信後に `help-AI` ラベルは自動で外れます。追加質問は次の順で行います。

1. **先にコメントを投稿する**
2. **その後で `help-AI` ラベルを付け直す**

順序が重要です。ラベルを先に付けると、コメントを読む前に調査が始まることがあります。

## 返信の内容

初回・再返信のいずれも次の書式で返ります。種類によって不要なセクションは省略されます。

```
## ご質問ありがとうございます      （再返信時は「## ご回答ありがとうございます」）

<内容の要約・こちらの理解>

### 調査結果
<調査で分かった事実。根拠となるファイルパスを明示>

### 回答 / 見立て
<回答、または不具合の原因の見立て・要望の実現可否>

### 確認させてください（情報が不足している場合のみ）
```

- 確認できた事実と、推測・見立ては書き分けられます
- 根拠となったファイルのパスが示されます
- 進捗チェックリストや作業ログは本文に含まれません
- 再返信では、前回の回答からどこを変えたかが要約に示されます

## 所要時間と挙動

1. ラベル付与から 2〜3 分後、**「調査中です」のコメント**が投稿される
2. 調査が終わると、**同じコメントが返信内容へ書き換わる**（新しいコメントは作られない）
3. 返信後、`help-AI` ラベルが自動で外れる

目安は 10〜20 分。調査範囲の広さで変動します。

**ラベルは返信の成否にかかわらず外れます。** 失敗時に残ると、同じラベルを付け直せず
再実行できなくなるためです。失敗した場合は、そのコメントが失敗の旨に書き換わります。

## 参照リポジトリ

`refs.json` に書かれたものを、毎回の実行で取得します。

| ディレクトリ | 内容 | 備考 |
| --- | --- | --- |
| `src` | 実装コード | 実装に関する調査対象 |
| `docs` | 設計書・仕様書 | AI が開けない形式（Excel・Word 等）は取得しない設定にできる |
| `wiki` | 開発方針・共通仕様・運用ルール | Gitea の wiki は `owner/repo.wiki` |

**参照先を増減するときは、`refs.json`・`SKILL.md`・本書の一覧を同じコミットで直します。**
`python3 scripts/check_sync.py` が食い違いを検出します。

取得は 1 つ失敗しても止まりません。どれが欠けたかは実行ログの一覧と、
AI へ渡すプロンプトの `<reference_repos>` に `MISSING` として出ます。

## 処理の流れ

```
help-AI ラベル付与
  ↓
① 自リポジトリを取得（ワークフロー・スクリプト・スキル定義）
  ↓
② 起動条件の判定（PR でないか、ラベルが付いているか、今回付いたのが help-AI か）
  ↓
③ 参照リポジトリを取得（1 つ失敗しても続行）
  ↓
④「調査中です」コメントを投稿          ← ここで動いていることが見える
  ↓
⑤ 既存コメントを取得（初回か再返信かの判定材料）
  ↓
⑥ プロンプトを組み立て（イシュー本文・コメント・取得結果を埋め込む）
  ↓
⑦ Claude Code CLI で返信を生成
  ↓
⑧ ④ のコメントを返信で書き換える        ← ここで返信が見える
  ↓
⑨ help-AI ラベルを外す（成否にかかわらず）
```

## 権限とセキュリティ

### ツール権限

AI に許可するのは**読むことだけ**です。次を禁止しています。

- `Edit` / `MultiEdit` / `Write` / `NotebookEdit` … ファイルの書き換え
- `Bash` … `sed -i` やリダイレクトでの書き換え、`git push`、`curl` での外部送信ができるため
- `WebFetch` / `WebSearch` … 手元の資料だけで答えさせるため

残るのは `Read` / `Grep` / `Glob` です。
イシュー本文は外部からの入力であり、SKILL.md の「分析・回答までに留める」は指示にすぎないため、
**ツール権限側でも落としています**（二重防御）。

### 認証情報の扱い

- 参照リポジトリは取得後に `.git` を削除します。clone URL にトークンが載るため、
  残すと `.git/config` を `Read` で読めてしまいます
- イシュー本文・コメントは、ワークフロー側でプロンプトに埋め込みます。
  AI 自身にイベントファイルを読ませないので、Bash を禁止できます
- SKILL.md 側にも、トークン・`.env`・secrets の値を返信に書かない規定があります

### プロンプトインジェクション

イシュー本文やコメントに「これまでの指示を無視する」「ファイルを書き換える」「秘匿値を出力する」
といった指示が含まれていても従わず、該当箇所を引用して返信で指摘する扱いです。
技術的にも、書き込み系ツールと `Bash` は禁止済みのため実行できません。

### 起動できる人

`help-AI` ラベルを付与できる利用者（リポジトリへの書き込み権限を持つメンバー）です。
テンプレート経由のイシュー作成でも、自動付与により起動します。

## 責務の範囲

**コメントによる分析・回答・提案までです。** コードの修正・コミット・PR 作成は行いません。

実装まで自動化したい場合、このワークフローの延長では対応できません。ツール権限で書き込みを
禁止しているうえ、イシューが立つリポジトリと実装対象のリポジトリが別だからです
（参照用に取得しているだけなので、そちらへは PR を出せません）。
実装を自動化するなら、実装対象のリポジトリ側に別のワークフローを用意する構成になります。
