# ADR-0003: 拡張を署名つきパッケージにする

- 日付: 2026-08-21
- 状態: 有効

## 背景

本体をタスク管理に絞ったうえで（[ADR-0004](0004-本体はタスク管理だけに絞る.md)）、
確定申告のような機能をオプションとして売りたい。将来はパッケージを増やしていきたい。

サーバーが無いため、「購入者の端末に、あとから機能を足す」方法が要る。

## 選択肢

| 案 | 評価 |
|---|---|
| 機能ごとに別の HTML を配る | データが分断される。タスクと連携できない。却下 |
| 全部入りを配り、キーで機能を開閉する | 使わない機能のコードも配ることになり、本体が太る。「基礎はタスク管理のみ」という方針に反する。却下 |
| `<script src>` で外部ファイルを読む | ファイルが複数になり「1 ファイル」の利点を失う。file:// での挙動もブラウザ差がある。却下 |
| **署名つきパッケージを読み込んで保存する** | 1 ファイルの利点を保ったまま機能を足せる。採用 |

## 判断

拡張を `.tdpkg`（JSON）として配る。中身は `{format, manifest, code, signature}`。
`{manifest, code}` を並び順の決まった JSON にして、ライセンスと同じ秘密鍵で署名する。

アプリは読み込み時と起動時に署名を確かめ、合格したものだけを `new Function` で実行する。
パッケージは localStorage に保存され、次回以降も自動で読み込まれる。

## 実行の隔離について

拡張はページと同じ文脈で動く。iframe や Worker には入れない。

- 実行するのは販売元が署名したコードだけなので、信頼の起点は署名にある
- 隔離すると、本体と同じ CSS で画面を描けなくなり、拡張が「別のアプリ」に見えてしまう

**第三者の拡張を売る場を作る場合は、この判断を見直す。**
その時点で、署名前のコード審査を運用に入れるか、Worker + メッセージ受け渡しへ作り替える。

## 帰結

- 拡張が 0 個なら、本体は拡張機構が無かったころと同じ動きをする
- 評価版と製品版で別のパッケージを配らずに済む（利用権はライセンスキー側に持たせた）
- パッケージ形式の互換性を、`apiVersion` で明示的に管理する必要が生まれた
