# 全体アーキテクチャ

TaskDeck が何でできていて、どういう順で動くかをまとめます。
引き継ぐ人が最初に読む文書です。

## 全体像

```
販売者の手元                          購入者の端末
─────────────                        ─────────────
keys/private.json  ──署名──┐
   (秘密鍵)                │
                          ├─→ TaskDeck.html ──開く──→ ブラウザ
extensions/tax/           │     （公開鍵を内蔵）        │
  manifest.json + main.js │                            │ localStorage
        │ pkg.py build    │                            ├─ taskdeck.data.v1      タスク
        └────署名────→ tax-1.0.0.tdpkg ──読込──→│─ taskdeck.license.v1   ライセンス
                          │                            ├─ taskdeck.plugins.v1   拡張パッケージ
keygen.py issue ──署名──→ TD1.…（ライセンスキー）─→ └─ taskdeck.ext.<id>.v1  拡張のデータ
```

サーバーはどこにもありません。署名する側（販売者）と検証する側（購入者の端末）が、
公開鍵ひとつでつながっています。

## 製品の構成

製品は **1 つの HTML ファイル**です。中は上から順に次のようになっています。

| 位置 | 中身 |
|---|---|
| `<style>` | 全画面ぶんの CSS。配色は CSS 変数（`--accent` など）で持ち、明暗テーマを切り替える |
| `<body>` | 骨格の HTML。ダイアログや詳細パネルも最初から置いてある（表示は CSS で制御） |
| `<script>` 冒頭 | `LICENSE_PUBLIC_KEY`（販売者が `keygen.py init` で書き込む 1 行） |
| `TaskDeckLicense` | 署名の検証。SHA-256 と P-256 を BigInt で実装（外部ライブラリなし） |
| 1〜6 節 | タスク管理の本体（保存・ライセンス・日付処理・絞り込み・描画・操作） |
| 6.5 節 | 拡張ホスト |
| 7〜8 節 | 画面のイベント接続と起動 |

節番号はソース中のコメントと対応しています。

## 起動の順番

```
boot()
 ├ load()          localStorage からタスクを読む（壊れていれば normalize() が直す）
 ├ loadLicense()   キーを検証する。不正・期限切れなら「評価版」として続行
 ├ loadPlugins()   拡張を読み、署名を確かめ、有効なものを実行する
 ├ wireEvents()    画面の操作をつなぐ
 └ render()        サイドバー・見出し・本体を描く
```

`render()` は「いまの状態から画面を作り直す」だけの関数です。
状態を変える処理（タスクの追加、拡張の入れ替えなど）は、最後に `save()` と `render()` を呼びます。
差分更新はしていません。扱う件数が数千件までなら、この単純さのほうが壊れにくいと判断しました。

## 描画の分かれ道

`data.settings.filter.type` で、中央に何を描くかが決まります。

| type | 中央に描くもの |
|---|---|
| `smart` | 今日・今週・重要・すべて・完了済み のいずれか（ボード or リスト） |
| `project` | そのプロジェクトのタスク |
| `tag` | そのタグのタスク |
| `plugin` | 拡張が登録した画面（タスクの入力欄と表示切替は隠れる） |

## 保存のしかた

- 変更のたびに `save()` を呼ぶ。実際の書き込みは 120 ミリ秒だけまとめる（連打で重くならないように）
- タブを閉じる・再読み込みする・隠れるときに `flushSave()` で書き残しをなくす
- 別タブで編集されたときは `storage` イベントで読み直す

## 拡張との境界

本体は拡張のことを、次の 3 つの入れ物としてしか知りません。

```
contributions = { views: [], taskPanels: [], exports: [] }
```

拡張が 1 つも入っていなければ、この 3 つは空のままで、
サイドバーの「拡張」欄も出ません。**拡張機構が無かったころとまったく同じ動き**になります。

詳しくは [拡張ホストの設計](拡張ホストの設計.md) を参照してください。

## 意図的にやっていないこと

| やっていないこと | 理由 |
|---|---|
| ビルド工程（バンドラ・トランスパイラ） | 1 ファイルで完結させるため。ソースがそのまま製品 |
| フレームワーク | 依存を持たないため。10 年後も同じファイルが動くことを優先 |
| サーバー同期 | 「データを外に出さない」ことが売りだから |
| 差分描画 | 単純さを優先。実測で問題が出たら考える |
| 拡張のサンドボックス実行 | [セキュリティ設計](セキュリティ設計.md) に判断の理由を書いています |
