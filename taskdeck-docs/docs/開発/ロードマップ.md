# ロードマップ

「いつか作るかもしれないもの」を並べた場所です。約束ではありません。
順番は、購入者からの要望と、実装の重さで決めます。

## いまあるもの（1.0）

- 本体: タスク管理（ボード / リスト、プロジェクト、タグ、サブタスク、期限、優先度、検索、書き出し）
- 拡張のしくみ: 署名つきパッケージ、独自画面・タスクパネル・書き出しの追加、ライセンスによる利用権
- 拡張: 確定申告データ管理（複式簿記）

## 次に来そうなもの

| 候補 | 中身 | 重さ | 備考 |
|---|---|---|---|
| 請求書作成（拡張） | タスクから請求書を起こし、印刷用の画面まで | 中 | 確定申告拡張と組み合わせると強い |
| 経費メモ（拡張） | 領収書の写真をその場で縮小して保存し、仕訳の下書きにする | 中 | 画像を localStorage に入れる設計の検討が要る |
| 勤怠記録（拡張） | 作業時間の記録と、月次の集計 | 小 | タスクとの相性がよい |
| 繰り返しタスク（本体） | 毎週・毎月の予定を自動で作る | 小 | 全員が使うため本体側 |
| 添付ファイル（本体） | タスクにファイルを紐づける | 中 | 保存容量の設計が必要 |

## 拡張のしくみに足すかもしれないもの

必要が出るまで足しません（一度公開した API は削れないため）。

- `registerQuickAddHandler` … 入力欄の記法を拡張が増やせるようにする
- `registerSettingsPane` … 拡張ごとの設定画面
- `on("tasks:changed")` … タスクの変更を拡張へ知らせる
- 拡張の保存データを、本体のバックアップに含める仕組み

## パッケージの市場を作る場合

「第三者が作った拡張を売る場」まで広げるなら、次の検討が必要になります。

1. **審査**: 署名する前に、販売者がコードを読む運用にするか
2. **隔離**: Worker + メッセージ受け渡しへ作り替え、拡張から DOM を触れなくするか
   （[ADR-0003](../設計/ADR/0003-拡張を署名つきパッケージにする.md) の判断を見直すことになります）
3. **鍵の分離**: 拡張の作者ごとに鍵を持たせ、本体が複数の公開鍵を信頼する形にするか
4. **収益の分配**: 決済と分配の仕組み。ここはサーバーが要る

1〜3 は設計の話、4 は事業の話です。順番としては、まず自社の拡張を 3〜4 本そろえ、
「拡張を足す」流れが購入者に受け入れられることを確かめてからで十分だと考えています。
